# REVIEW: Шаг 4 — возврат латентности (сплит геометрии и времени)

Исполнитель: Cline. Бриф: `docs/BRIEF-router-latency.md` (Gemini). Дата: 2026-09-17.
Проверка «писатель ≠ проверяющий»: бриф писал Gemini, реализацию и метрики — Cline,
эталонные ответы сверялись машинно (bайт-в-байт, ниже).

## 1. Что сделано

`router_layer.py`:

- `_approaching_vehicles(route_key, board_node)` — **пространственная** часть:
  кто едет к остановке и через сколько минут (`eta` + `live_bus` / `is_live` /
  `route_label`). Список отсортирован по `eta`, живёт в `_spatial_cache`.
- `_nearest_live_vehicle(route_key, board_node, board_time)` — **временная** часть:
  проходит по готовому списку и возвращает первую машину, которая приедет не
  раньше пассажира (допуск `BOARD_TOLERANCE_MIN = 0.5`), считает `wait_min`
  от прибытия пассажира. Логика Шага 3 не изменена.
- `set_live()` — подпись геометрии парка (`_fleet_fingerprint`, поля
  `lat/lon/speed_kmh/board_number/is_live/route_label`) и версия парка
  (`_fleet_version`): кэш сбрасывается только когда геометрия реально изменилась.
- Записи кэша помечены версией парка, поэтому устаревшая запись не может попасть
  в ответ; `_spatial_cache.clear()` вместо перепривязки — безопасно для потоков
  FastAPI (`TransitRouter` обслуживает несколько запросов одновременно).

Итог: haversine считается один раз на `(маршрут, вузол)` на актуальный срез
парка, а не на каждый заход Дейкстры (тысячи заходов на один `plan()`).

## 2. Три правки к брифу (почему «как написано» не работает)

1. **Кэш нельзя вешать на экземпляр без инвалидации.** В брифе ключ описан как
   `(route_key, board_node)` «на уровне экземпляра». Позиции ТС меняются на
   каждом опросе GPS, и без инвалидации ответ после следующего опроса строился бы
   по старой геометрии. Добавлена версия среза + сброс.
2. **Сброс «на каждый `set_live()`» делает кэш вечно холодным.** Прод-эндпоинт
   `/api/plan` зовёт `router.set_live(...)` **внутри обработчика запроса**
   (`main.py:801`), а опрос GPS идёт реже, чем запросы: между опросами позиции
   одни и те же. Поэтому сброс привязан не к факту вызова, а к смене геометрии
   (подпись). Без этой правки выигрыш был бы только внутри одного `plan()`
   (4× по haversine), с ней — ещё и между запросами внутри одного опроса.
3. **`eta` в кэше — сырое число, округление только на выходе.** В ответе
   `eta_min` округляется до 0.1, но `wait_min` считается как
   `max(0.5, round(wait_after_arrival + 0.5, 1))` — если бы в кэш легло уже
   округлённое `eta`, граничные случаи дали бы другой `wait_min`.

Плюс мелочи: `route` больше не ищется в `self.routes` на каждом заходе (проверка
`route_key in self.routes` внутри кэширующего метода), а сортировка по `eta`
эквивалентна прежней сортировке по ожиданию (`eta - arrive_min` монотонно по
`eta`), поэтому выбор «первого ТС» не изменился.

до и после правки: `IDENTICAL ... True` во всех шести случаях
(`latency4.py` + `latency4_cmp.py`, слепки `latency4_before.json` /
`latency4_after.json`). Менялись только время и счётчик haversine.

Тесты: было 7, стало **10** (все проходят, `pytest` ~1.5 с):

- `test_spatial_cache_does_not_change_result` — кэш это только ускорение: ответ
  совпадает с прогоном, где кэш очищается перед каждым заходом;
- `test_same_fleet_keeps_spatial_cache` — тот же парк (даже с другим
  `snapshot_at`) не сбрасывает геометрию и даёт тот же ответ;
- `test_spatial_cache_drops_stale_fleet` — сменились позиции: версия растёт, кэш
  пуст, ответ совпадает с «чистым» роутером на новом парке.
