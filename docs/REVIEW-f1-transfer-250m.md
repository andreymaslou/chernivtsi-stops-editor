## 3. Фильтры применяются только к новой полосе (иначе ломается план)

Три варианта на 36 случайных парах:

| Вариант | Пересадок | Планов изменено | Что не так |
|---|---|---|---|
| baseline (150 м, без фильтров) | 194 | — | кейс §1.7 недостижим |
| **A: фильтры везде** | 108 | 11 из 36 | удаляет 156 legacy-рёбер: «Онколікарня → вул. Гетьмана Дорошенка» **75 мин / 20 грн / 0 пересадок → 112 мин / 60 грн / 2 пересадки** |
| **B: фильтры только > 150 м** | 292 | 11 из 36 | принят: ухудшений нет, эффект тот же |

A и B отличаются ровно на 1 паре из 36, и это ухудшение — отсюда правило
`TRANSFER_LEGACY_MAX_METERS`.

## 4. Правило «соседних остановок» учитывает набор маршрутов

Первая версия фильтра («пропускать любую пару, соседнюю в цепочке одного направления»)
дала регресс: у узла `202` осталось **ноль** соседей — ребро `202↔140` (пара подряд в
`bus:23:B`) отфильтровалось, и прямой 20-й снова стал недостижим. Из 40 отфильтрованных
пар у **33** наборы маршрутов на концах **разные** — это не «пройти вдоль своего маршрута»,
а реальный вариант сесть на маршрут, который идёт только от соседней остановки.
Итоговое правило: пропускаем только если наборы маршрутов на обоих концах **совпадают**.

## 6. Блокер: 3 из 6 эталонных планов изменились, один — в худшую сторону

Эталоны `latency_plan.py`: `PAIRS = [(107,166), (181,166), (166,107)]` × 2 сценария (night 03:10,
day 12:00) с живым парком (`snapshot_fleet`).

| Сценарий | Пара | Было | Стало | Оценка |
|---|---|---|---|---|
| night 03:10 | 107→166 | 33 мин / 32 грн / 1 пер. | 32 мин / 36 грн / 1 пер. | смешанно (−1 мин, +4 грн) |
| night 03:10 | 181→166 | 50 мин / 56 грн / 2 пер. | **39 мин / 40 грн / 1 пер.** | **лучше** (−11 мин, −16 грн, −1 пересадка) |
| night 03:10 | 166→107 | 33 мин / 36 грн / 1 пер. | без изменений | — |
| day 12:00 | 107→166 | 34 мин / 20 грн / 0 пер. (9A) | без изменений | — |
| day 12:00 | 181→166 | 50 мин / 56 грн / 2 пер. | **64 мин** / 56 грн / 2 пер. | **хуже** (+14 мин) |
| day 12:00 | 166→107 | 35 мин / 60 грн / 2 пер. | без изменений | — |

**Почему это не может быть «так вышло».** Новый граф — надмножество рёбер старого (рёбра
≤ 150 м сохранены без изменений, §3). Старый план «5 → 10 → 33» остаётся выполнимым в новом
графе: его пересадки — рёбра `(11,15)` и одна из `(9,10)/(9,17)/(10,17)`, все на месте.
При том же парке и том же `now` его стоимость не могла вырасти. Значит роутер его просто
**не нашёл**.

**Причина (в коде).** В `_dijkstra` ключ состояния — `state = (route_key, node)`
(`router_layer.py:562`, `:577`, `:601`, `:625`) — **не включает набор использованных
маршрутов** (`used`), хотя `used` применяется для отсечения повторных посадок (`:615`).
Дешёвый ярлык с «плохим» набором маршрутов вытесняет из `dist` более дорогой ярлык с
«хорошим» набором, и продолжение, которое могло бы дать лучший итог, теряется.
Больше рёбер → больше ярлыков → чаще вытеснение: порог 250 м **вскрыл** этот дефект.

**Масштаб (замерено).** На 40 случайных парах с живым парком регрессий нет:
night — 0 медленнее / 9 быстрее / 30 так же; day — 0 медленнее / 11 быстрее / 28 так же.
То есть дефект редкий, но реальный — и эталонный набор его поймал.

## 7. Решения, которые нужно принять (блокируют выпуск поставки 1)

1. **Починить ярлыки (рекомендую).** Включить `used` в ключ состояния (`dist`/`prev`) либо
   ограничить «набор» окном последних 1–2 маршрутов. Корректно, но состояние растёт →
   нужен отдельный замер латентности и отдельный пере-бейзлайн (планы изменятся широко).
2. **Выпустить с задокументированным ухудшением.** Не рекомендую: цель F1 — лучшее качество
   выдачи, а не «в среднем лучше».
3. **Отложить F1.** Код остаётся в ветке, `main` не трогаем (порог сам по себе не даёт
   гарантии «не хуже»).

До решения по п.1 порог 250 м **не выпускать** и не деплоить: `main` остаётся на 150 м.

рабочего дерева, поэтому A/B по графу делается двумя копиями `graph.json` (или через
`git show HEAD:graph.json`), а не ключом `--rev`.
