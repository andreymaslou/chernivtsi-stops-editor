# REVIEW: карта плану маршруту (хвости, напрямок, номери кроків)

Обновлено: 2026-09-17. Задача: довести карту плана до вида «зрозуміло з першого
погляду» — пасажир бачить, **куда** їде його маршрут (а не тільки свою ділянку),
**в яку сторону**, **де саме його посадка** і **де кінець**.

## 1. Что сделано

| Слой | Правка |
|---|---|
| `router_layer.py` | `leg.full_geom` — полная геометрия направления (весь ланцюжок остановок маршрута). Для пеших ног не отдаётся: у них геометрии нет |
| `web/emulator.js` | хвост маршрута, шевроны направления, бейдж кроку, финиш, иконка пешего отрезка, слой на каждую ногу, `esc()` для строк из API |
| `web/emulator.html` | стили `.plan-*`/`.step-dot`, `@media (prefers-reduced-motion: reduce)` |
| `tools/ui/check_emulator.js` | 11 новых машинных проверок (31 → **42 OK**) |
| `tools/perf/compare_snapshots.py` | `--ignore-keys` + путь первой разницы |

### 1.1 Хвост маршрута (контекст)

`leg.path` — это только наша ділянка (наприклад, 6 остановок из 30). Теперь
сервер отдаёт `leg.full_geom` — весь ланцюжок напрямку, а клиент рисует **хвіст**:
срез `full_geom`, расширенный на `TAIL_CLIP_STOPS = 6` остановок в каждую сторону,
`opacity 0.3`, `weight 4` против активных `0.9`/`6`.

**Почему обрезка на клиенте, а не на сервере:** полный маршрут через весь город —
это 30+ точек на каждую ногу, и на экране это «простыня» вместо подсказки. Обрезка
на клиенте позволяет менять длину хвоста без правки API (и без деплоя).

**Инвариант:** `path` обязан быть непрерывным срезом `full_geom`
(`full_geom[i:j+1]`), иначе хвост не стыкуется с активной линией. Закреплено
тестом `test_leg_full_geom_covers_active_path` (и в контрактном тесте:
`len(full_geom) >= len(path) >= 2`). Клиент, не найдя срез, просто не рисует
хвост (`sliceOffset()` → -1) — деградация мягкая.

### 1.2 Направление: шеврон вместо отдельной стрелки

`leaflet-polylinedecorator` с unpkg **сознательно не подключён**: при недоступности
CDN карта молча осталась бы без стрелок, а headless-проверка зависела бы от сети
(та же беда, что недавно чинили у тайлов OSM). Вместо плагина — маленький
`L.divIcon` с SVG-шевроном:

* шеврон внутри **точки промежуточной остановки** (один маркер вместо двух:
  «здесь остановка» + «маршрут едет туда») — 18 px, цвет `var(--route-colour)`.
  Координаты промежуточных остановок приходят отдельным массивом `leg.stops`
  (точки OSRM-геометрии дороги для этого не подходят — их сотни);
* отдельный шеврон — не «на каждом сегменте > N м», а при накоплении длины
  линии: считаем расстояние по точкам `leg.path` и ставим шеврон в середине
  той точки, где накоплено `ARROW_MIN_SEGMENT_M` (800 м), потом счётчик
  сбрасываем. Иначе на OSRM-геометрии (много коротких сегментов) шевроны
  слипаются в одну кучу;
* поворот — `transform: rotate(<азимут>deg)`, азимут считается той же формулой,
  что в роутере (`bearingDeg()`), и лежит в `data-bearing` вместе с `data-lat`/
  `data-lon` — по ним проверка сверяет угол с ответом сервера.

### 1.3 Номера кроків и финиш

* `stepBadge()` — крупный (30 px) круг с номером ноги в **цвете маршрута**
  (`leg.color`), с пульсацией `pulse-step 1.6s`; ставится в точку посадки;
* финиш 🏁 — по координате остановки назначения (`state.stops[plan.to_stop_id]`),
  с фолбэком на конец последней поездки: последняя нога бывает пешей, и её
  геометрии может не быть вовсе;
* в текстовой панели вместо `1️⃣`/`2️⃣` — тот же номер в кружке своего цвета
  (`.step-dot`), и **клик по нему зумит карту к этой ноге**
  (`state.planStepLayers[step]` → `map.fitBounds`). Заодно исправлен баг: третья
  нога показывалась как `2️⃣` (было `isFirst ? '1️⃣' : '2️⃣'`).

### 1.4 Пешая пересадка

Геометрии пересадки роутер пока не отдаёт, поэтому раньше пешая нога **вообще не
рисовалась**. Теперь, если `leg.path` у пешей ноги нет, берётся прямая между
концом предыдущей поездки и началом следующей (это реальные точки остановок), и
на середине ставится 🚶. Пунктир остался прежним (`#808080`, `dashArray '1, 10'`,
`lineCap/lineJoin: round`) — менять его на `'5, 8'` было бы регрессом, проверка
это фиксирует.

### 1.5 Прочее

* каждая нога — свой `L.layerGroup` внутри общего `layerGroup` (уборка по-прежнему
  одной строкой `clearLayers()`, но теперь есть адресация «шаг → линия»);
* `esc()` добавлен для `leg.route` / `from` / `to` / `at` / `live_bus` /
  `vehicle_state`: эти строки приходят из справочника и LLM, а вставлялись в
  `innerHTML` сырыми (та же дисциплина, что в попапе машины);
* в легенду добавлен 5-й ряд «Крок плану» (кружок с цифрой) — на карте появился
  новый визуальный элемент, значит он обязан быть в легенде;
* `state.lastPlan` — последний ответ сервера (нужен проверке, пригодится и для
  будущих «перерисовать без запроса»).


## 2. Проверки (машинные)

```powershell
python -m pytest -q                       # 16 passed (было 15)
node tools\ui\check_emulator.js           # 42 OK (было 31)
```

Новые ассерты UI-проверки (11):

1. номера кроков на карте: бейджей столько же, сколько поездок (`[1,2]`);
2. бейдж крупный (≥ 28 px) и с непустой анимацией (`pulse-step`);
3. цвет бейджа = `leg.color` (сверка `background` с ответом сервера);
4. шевроны направления: их > 0 и **у всех** угол совпадает с азимутом,
   пересчитанным из `leg.path` (допуск 0.6°);
5. точек промежуточных остановок ровно `sum(len(path) - 2)`;
6. хвостов столько же, сколько поездок, и их `stroke-opacity` (0.3) меньше
   активной линии (0.9) — но больше нуля;
7. иконка 🚶 на пешей ноге + пунктир нарисован (синтетический план: пешая нога
   **без** геометрии → проверяется новый фолбэк «прямая между остановками»);
8. `stroke-dasharray` пешей ноги не изменился (`1, 10`);
9. финиш ровно один;
10. цифры кроков в панели = номерам бейджей на карте;
11. при `prefers-reduced-motion: reduce` пульсация выключается.

Легенда: проверка обновлена с 4 на 5 рядов (+ свотч «Крок плану»: белая цифра на
синем круге).

Пеший отрезок проверяется **синтетическим планом** (как CSS-правила `stopped`):
на реальных фразах пешей ноги может не быть вовсе (старт и финиш совпадают с
остановками посадки) — проверка не должна зависеть от расписания дня.

## 4. Грабли и ограничения

1. **`full_geom` — это остановки, а не геометрия дорог.** Хвост на длинном
   перегоне выглядит угловатым (прямая между остановками). Это тот же компромисс,
   что и у активной линии; настоящие way-линии OSM — отдельная задача.
2. **Пеший отрезок — прямая** между остановками (геометрии пересадки у роутера
   нет). Когда роутер начнёт отдавать `leg.path` для пеших ног, код автоматически
   возьмёт её (`isWalk && leg.path.length > 1`), а фолбэк останется для старых
   ответов.
3. **При `zoom < 13`** разгрузка (`body.zoom-out`) касается только маркеров ТС;
   бейджи кроков и шевроны не сжимаются. На общем виде города это читается
   нормально (бейджи крупные и цветные), но если дизайн захочет — это ещё одна
   строка CSS (`.zoom-out .plan-step { transform: scale(.7) }`).
4. **Headless Chromium отдаёт `prefers-reduced-motion: reduce`**, поэтому
   пульсация в проверке «сама выключилась». Проверка явно просит
   `no-preference` (`page.emulateMediaFeatures`) и отдельным ассертом фиксирует,
   что при `reduce` анимация действительно `none`.
5. **`state.lastPlan` доступен из `page.evaluate`** (верхнеуровневый `const` в
   классическом скрипте — как `map` и `state.stops`). На этом построены сверки
   «карта против ответа сервера».
6. **`className` у `L.polyline`** (`.plan-tail`, `.plan-active`, `.plan-walk-line`)
   работает в Leaflet 1.9 — это способ отличить линии в DOM, не заводя свои слои
   для каждой. Стили линий всё равно задаются опциями (`opacity`, `weight`), а не
   CSS: проверка читает `stroke-opacity` через `getComputedStyle`.

## 5. Что осталось (не входило в задачу)

1. Настоящая пешая геометрия пересадки (роутер → `leg.path` для `walk`).
2. OSM way-линии вместо прямых между остановками (общая задача §5.3 STATUS).
3. `MAX_LIVE_SNAP_METERS` 600 → 150–250 (задача §5.7 STATUS) — не связано с картой,
   но следующий шаг по точности «первого нужного ТС».
