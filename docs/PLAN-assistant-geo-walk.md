## 0. Контекст: для кого фича

Кнопка «(AI-ЗАПИТАЙ МЕНЕ)» — **помощник, а не основной сценарий**: для тех, кто не
знает города (пенсионеры, новые студенты, переселенцы, туристы). Местным прорисовка
маршрутов не нужна — им нужно «куда ехает ТС и в мою ли сторону». Дальше из этой же
кнопки, возможно, вырастет короткий диалог («а через сколько следующий?») — над этим
уже работают. Реклама/офферы по геолокации во время поездки — отдельный этап позже.

Пользователь приложения часто **не включает GPS** — это обязательный фолбэк, а не
крайний случай.

## 1. Что уже сделано (шаг 1 — голос)

  toast — `navigator.permissions` → `microphone` решает, что показать:

  браузер после отказа больше НЕ спрашивает сам. `NotAllowedError` в `onerror`
  тоже открывает режим denied. Разметка `#voice-perm-modal` в `editor.html`,
  стили `.perm-body` в `style.css`, логика — `emulator.js` (voiceModal*).
* Smoke-тест: `node tools/ui/check_voice.js` (шесть сценариев: мок Web Speech при
  granted, браузер без поддержки, реальный Web Speech, шторка 'prompt', шторка
  'denied', небезпечний контекст — сценарий F).
* **HTTPS включён (2026-09-23)** — то, без чего голос не работал вообще: стенд
  отдаётся как `https://169.58.82.105.nip.io/` (nginx + Let's Encrypt + Basic
  Auth), `:8000` наружу закрыт. До этого на `http://<IP>` браузер блокировал
  микрофон целиком (`permissions` сразу `denied`, `mediaDevices` отсутствует) —
  именно поэтому кнопка «не подключалась». Шторка теперь различает случаи: при
  небезопасном соединении показывает «🔒 Потрібен HTTPS» вместо инструкций по
  настройке микрофона (`voiceInsecure()`, `mode: 'insecure'`). Детали — §5.1 в

## 2. Шаг 2 — «точка выхода»: фраза → карта → GPS

Точка выхода — это **не обязательно текущее местоположение пользователя**. Пользователь
может строить маршрут для подруги, друга или члена семьи, который находится в другой
части города. Поэтому фича называется «точка выхода», а поле API не должно называться
`my_pos`.

Приоритет источников старта:

1. **Явная точка, выбранная на карте.** Это основной режим: он работает без GPS и
   позволяет указать место, откуда на самом деле начинается поездка.
2. **GPS пользователя** — дополнительный быстрый режим «Я здесь», только по явному
   нажатию и разрешению браузера.
3. **Начало, извлечённое из текста** — «я на Соборці», «від Соборної».
4. Если ничего нет — вернуть `clarify`.

Выбранная на карте точка является источником истины: GPS пользователя не должен
молча заменять её. Если в тексте одновременно назван другой старт, UI показывает
конфликт и просит подтвердить выбор; в MVP допустимый простой fallback — явно
показать выбранную карту как приоритетную.

**API:** добавить в `PlanRequest` не `my_pos`, а:

```json
{
  "text": "До Гравітону",
  "start_pos": {"lat": 48.29, "lon": 25.93},
  "start_source": "map"
}
```

`start_source`: `map | gps | text`. Если старт уже назван в тексте, `start_pos` можно
не передавать. Старые naive-даты и модельное время здесь не смешиваем: координаты —
JSON, временная модель проекта — `Europe/Kyiv`.

**Бэкенд:** добавить `start_pos` в `PlanRequest` (`main.py`) и вернуть в ответе
`origin.source`, чтобы UI мог показать, откуда взялась точка выхода.

**Грабли:** Web Speech и Geolocation **не работают на простом HTTP** (кроме localhost).
**Уже закрыто (2026-09-23):** стенд переведён на HTTPS — `https://169.58.82.105.nip.io/`
(nginx + Let's Encrypt + Basic Auth, бэкенд только на `127.0.0.1:8000`); в браузере
`isSecureContext = true`, `permissions.microphone = 'prompt'`. Для боевого домена
нужна своя A-запись: текущий `transgps.cv.ua` ведёт не на наш VPS (см. `STATUS.md` §5.1).

## 3. Шаг 3 — пеший путь до выгодной остановки

**Решение (зафиксировано): на первых порах — пунктир по прямой.** ОSM-линии — на
потом (данные OSM меняются; грубость первых версий юзера не пугает — путь
декоративно-навигационный, цифры честные).

* **Куда рисуем:** от выбранной точки выхода (`start_pos`) до `board_node` **выбранного
  варианта** из карточек. Порядок: запрос → карточки вариантов → выбор → пеший путь до
  посадочной остановки этого варианта. `start_pos` может принадлежать другому человеку,
  это нормально.
* **Почему не «просто ближайшая остановка»:** ближайшая может вести в другую сторону
  или по «не тому» направлению — см. `BRIEF-router-direction.md` (до фикса было
  1149 встречных пар). Выбор цели — после выбора варианта, не раньше.
* **Что уже готово в коде:**
  * пеший граф — `graph.json`, 194 ребра (`meters`, `walk_minutes`;
    `WALK_SPEED_KMH=4.5`, `DETOUR_FACTOR=1.25`, `NODE_MERGE_METERS=20` в
    `graph_layer.py`) — время в пути уже честное, с запасом на извилистость;
  * роутер уже отдаёт ноги `{type: "transfer", kind: "walk", walk_min, wait_min}`
    (стартовая/финальная прогулка);
  * UI ждёт готовый: пунктир `dashArray: '1, 10'` + иконка 👟 для walk-ног
    приготовлены в `emulator.js` (по `path`, которого у walk-ног пока нет).
* **Что достроить:** бэкенд отдаёт walk-ноге `path` = [точка юзера, `board_node`]
  (две координаты) → фронт рисует существующим правилом.
* **Тот же механизм потом закроет пешую пересадку** (геометрии transfer-walk роутер
  тоже ещё не отдаёт — тот же known issue).
* **Миграция на OSM — без смены контракта:** бэкенд в том же поле `path` начинает
  отдавать цепочку точек по way-линиям, UI не меняется.

**Границы пунктира (честно):** прямая может пройти «сквозь» двор/реку — в центре
терпимо, у Прута/в частном секторе юзер ищет мост. Погрежные случаи — первый
кандидат на OSM-версию.

## 3.1. Приоритет вариантов поездки

Дешёвый вариант не должен автоматически становиться лучшим: экономия нескольких гривен
не всегда стоит лишней пересадки или ожидания. Для MVP предлагаем честную иерархию:

1. **Основной вариант** — минимальное полное время с учётом ожидания, поездки и пешего
   пути. Это то, что чаще всего нужно пассажиру.
2. **Вариант без пересадок** — показывать выше карточки с пересадками, если он медленнее
   не более чем на 10–15 минут. Пересадка — это не только цена, но и дополнительный
   риск опоздать: следующий рейс может задержаться.
3. **Дешёвый вариант** — предлагать как альтернативу, если он экономит существенную
   сумму, а задержка невелика. Для первого порога можно использовать: до 5 минут
   дополнительного времени или экономия от 8–10 грн, но значения нужно проверить
   телеметрией.
4. Если дешёвый вариант одновременно убирает пересадку, он получает приоритет независимо
   от небольшой разницы во времени.
5. Если разница слишком велика, дешёвый вариант не должен называться «лучшим» —
   карточка должна явно показывать компромисс: «дешевле на X грн, но на Y минут дольше
   или с пересадкой».

Текущий `build_variants()` уже полезен как основа: он сравнивает быстрый вариант с
вариантом «≤1 пересадка». Следующим шагом стоит добавить явные метки и, возможно,
третий кандидат «дешевле», не меняя корневой план. До появления телеметрии не стоит
делать жёсткий полный Pareto-фронт — достаточно двух или трёх понятных карточек.

Особенность текущих данных: в замерах прямой вариант там, где он существует, обычно
является и оптимумом по времени; массовой альтернативы «прямой медленнее пересадочного»
пока нет. Поэтому default «самый быстрый» остаётся правильным, а «без пересадок» —
это UX-альтернатива, а не безусловная замена default.

## 4. Интеграция с приложением (RN) — флаг на будущее

Кнопку в приложении вклеивает друг (React Native, экраны уже отрисованы). Если веб
попадёт в **WKWebView** (iPhone), `webkitSpeechRecognition` внутри может не работать
(микрофон вебвью спрашивает отдельно). **План Б:** нативное распознавание
(`@react-native-voice/voice`) пишет текст в поле, вебу приходит уже текст.
Логика: кнопка в приложении — нативная, веб — исполнитель.
