## 0. Контекст: для кого фича

Кнопка «(AI-ЗАПИТАЙ МЕНЕ)» — **помощник, а не основной сценарий**: для тех, кто не
знает города (пенсионеры, новые студенты, переселенцы, туристы). Местным прорисовка
маршрутов не нужна — им нужно «куда ехает ТС и в мою ли сторону». Дальше из этой же
кнопки, возможно, вырастет короткий диалог («а через сколько следующий?») — над этим
уже работают. Реклама/офферы по геолокации во время поездки — отдельный этап позже.

Пользователь приложения часто **не включает GPS** — это обязательный фолбэк, а не
крайний случай.

## 2. Шаг 2 — «где я»: фраза → GPS → тап на карте

Приоритет источников «откуда ехать» (все три равноправны, GPS — не обязательный):

1. **Из фразы.** «Я на Соборці» → LLM уже вытащил `from`, геолокация не нужна вообще.
   Это самый частый и самый дешёвый путь.
2. **GPS.** `navigator.geolocation.getCurrentPosition` — только если юзер разрешил.
3. **Тап по карте.** Полноценный фолбэк для тех, у кого GPS выключен/запрещён:
   режим «укажите, где вы» → клик по карте → координаты. Конфликт с редактором
   решается существующим механизмом `setEditorEditMode` (клик-режим редактора
   на это время выключается).

**Бэкенд:** добавить `my_pos: {lat, lon}` в `PlanRequest` (`main.py:910`) — поле
уже заложено в контракт `EMULATOR_PLAN.md` §3, но в живом коде его нет (только
`text` и `now`).

**Грабли:** Web Speech и Geolocation **не работают на простом HTTP** (кроме localhost)
— в проде обязателен HTTPS (`deploy/setup-https.sh`; внимание: текущий DNS
`transgps.cv.ua` указывает не на наш VPS, см. `STATUS.md` §5 п.1).

## 3. Шаг 3 — пеший путь до выгодной остановки

**Решение (зафиксировано): на первых порах — пунктир по прямой.** ОSM-линии — на
потом (данные OSM меняются; грубость первых версий юзера не пугает — путь
декоративно-навигационный, цифры честные).

* **Куда рисуем:** от точки юзера (`my_pos`) до `board_node` **выбранного варианта**
  из карточек. Порядок: запрос → карточки вариантов → выбор → пеший путь до
  посадочной остановки этого варианта.
* **Почему не «просто ближайшая остановка»:** ближайшая может вести в другую сторону
  или по «не тому» направлению — см. `BRIEF-router-direction.md` (до фикса было
  1149 встречных пар). Выбор цели — после выбора варианта, не раньше.
* **Что уже готово в коде:**
  * пеший граф — `graph.json`, 194 ребра (`meters`, `walk_minutes`;
    `WALK_SPEED_KMH=4.5`, `DETOUR_FACTOR=1.25`, `NODE_MERGE_METERS=20` в
    `graph_layer.py`) — время в пути уже честное, с запасом на извилистость;
  * роутер уже отдаёт ноги `{type: "transfer", kind: "walk", walk_min, wait_min}`
    (стартовая/финальная прогулка);
  * UI ждёт готовый: пунктир `dashArray: '1, 10'` + иконка 👟 для walk-ног
    приготовлены в `emulator.js` (по `path`, которого у walk-ног пока нет).
* **Что достроить:** бэкенд отдаёт walk-ноге `path` = [точка юзера, `board_node`]
  (две координаты) → фронт рисует существующим правилом.
* **Тот же механизм потом закроет пешую пересадку** (геометрии transfer-walk роутер
  тоже ещё не отдаёт — тот же known issue).
* **Миграция на OSM — без смены контракта:** бэкенд в том же поле `path` начинает
  отдавать цепочку точек по way-линиям, UI не меняется.

**Границы пунктира (честно):** прямая может пройти «сквозь» двор/реку — в центре
терпимо, у Прута/в частном секторе юзер ищет мост. Погрежные случаи — первый
кандидат на OSM-версию.

## 4. Интеграция с приложением (RN) — флаг на будущее

Кнопку в приложении вклеивает друг (React Native, экраны уже отрисованы). Если веб
попадёт в **WKWebView** (iPhone), `webkitSpeechRecognition` внутри может не работать
(микрофон вебвью спрашивает отдельно). **План Б:** нативное распознавание
(`@react-native-voice/voice`) пишет текст в поле, вебу приходит уже текст.
Логика: кнопка в приложении — нативная, веб — исполнитель.
