# REVIEW: F4 — что показывать без живого борта и как быть с расхождением «план / борт»

**Дата:** 2026-09-21. **Статус:** **V3 выбран владельцем и реализован** (коммит `6987b49`);
замеры, три варианта, приёмка и остаток — ниже.
**Основание:** `docs/BRIEF-plan-variants.md` §12.4 (F4 входит в поставку 1) и §12.2 (контракт лога
телеметрии: `source`, `had_live_data`). **Репозиторий:** `e20e13d`.

## 1. Как это работает сейчас (по коду)

* базовое ожидание — `headway/2`, а если расписания нет — `DEFAULT_WAIT_MINUTES = 8`
  (`router_layer.py:927`);
* живой борт **только уменьшает** ожидание: `wait_min = min(live_wait, base_wait)`
  (`router_layer.py:944-946`), поэтому оптимистичная цифра расписания может остаться на экране;
* UI показывает **обе цифры рядом** (`web/emulator.js:748` и `:752-754`):
  `чекати ~5.2 хв` и `↳ сідати: 5346, буде ~6.9 [live]` — то самое расхождение §2 п.5 брифа;
* вне окна работы план не строится: API отдаёт `mode: "no_route"` и ноту
  «На цьому напрямку зараз нічого не їде — перший рейс орієнтовно о HH:MM» (`main.py:825-852`).

## 2. Замеры

Условия: 7 слотов времени × 30 случайных пар остановок (seed 33), сим-парк
(`common.snapshot_fleet`, как на стенде при `GPS_SIMULATOR=1`), `assume_in_service=True`,
граф 250 м / 292 пересадки.

### 2.1 Как часто нет живого борта

| Слот | Запросов | Без живого борта во **всех** ногах плана | Доля |
|---|---|---|---|
| 03:10 ночь | 30 | 16 | 53 % |
| 07:00 утро | 30 | 19 | 63 % |
| 08:30 час пик | 30 | 18 | 60 % |
| 12:00 день | 30 | 18 | 60 % |
| 17:30 час пик | 30 | 17 | 57 % |
| 19:00 вечер | 30 | 16 | 53 % |
| 23:00 поздний | 30 | 27 | **90 %** |
| **Итого** | **210** | **131** | **62 %** |

Ноги выигравших планов: **718**, с живым бортом — **149 (20.8 %)**. То есть в большинстве
случаев пассажир видит цифру расписания, и это не дефект данных, а норма: живой борт попадает
в ногу только когда он подходит по времени и направлению.

### 2.2 Расхождение «план против борта»

Сравнение показанного ожидания с честным живым (`live_wait` из `_nearest_live_vehicle`) — то
есть случай, когда `min()` оставляет расписание, а названный борт приедет позже:

| Метрика | Значение |
|---|---|
| ноги с живым бортом, где живой **медленнее** расписания | **29 из 149 (19.5 %)** |
| медиана скрытого расхождения | **+1.75 мин** |
| p90 | +6.55 мин |
| максимум | **+14.2 мин** |
| планы, у которых сумма таких расхождений > 0.15 мин | **27 из 210 (13 %)** |

Нижняя оценка цены «честного живого» (без пересчёта маршрута): те же 27 планов, медиана
**+2.7 мин**, максимум **+14.2 мин**.

Контрольный замер по всему поиску (1 292 884 вычисления ожидания за те же прогоны): живых
**4.1 %**, из них медленнее расписания **21.2 %** (медиана +3.35, p90 +8.65, максимум **+33.45**).
Разница с 19.5 % выше объяснима: поиск оценивает много тупиковых вариантов, а доля в
выигравшем плане меньше — для UI важна вторая цифра.

### 2.3 Прод-режим (без «предполагаем обслуживание»)

| Слот | Планов из 30 | Что отдаёт API |
|---|---|---|
| 03:10 | **0** | `mode: no_route` + «перший рейс орієнтовно о …» |
| 08:30 | 30 | обычный план |
| 23:00 | 2 | для остальных — `no_route` |

**Оговорка:** сим-парк «щедрый» — машины есть на всех маршрутах, поэтому в проде без живого
трекера (ночь при `GPS_SIMULATOR=0`, пустой срез, трек старше 5 мин) доля «без живого» будет
**выше** 62 %. Контрольный замер надо делать на реальном снимке трекера (он лежит вне
репозитория, см. `03eaed4`).

## 3. Три варианта поведения при `headway/2`

| | **V1 — как сейчас** `wait = min(live, headway/2)` | **V2 — честный живой** `wait = live_wait`, если борт есть | **V3 — min + явная вторая цифра** |
|---|---|---|---|
| В UI | `чекати ~5.2 хв` **и** `↳ сідати: 5346, буде ~6.9 [live]` | `чекати ~6.9 хв` + `↳ сідати: 5346 [live]` | `чекати ~5.2 хв (розклад)` + `↳ живий 5346 — через 6.9 хв` |
| В голосе | «чекати ~5 хв» | «чекати ~7 хв» | «орієнтовно 5 хв; живий борт — за 7» |
| Сумма цифр ног = `total_min` | **нет** (в 29 из 149 ног с живым бортом) | **да** | нет, но расхождение объяснено текстом |
| Плюсы | план оптимистичен, ловит живой борт, когда он раньше | одна цифра, нет противоречия, «честный пессимизм» | план не меняется, противоречие объяснено словами |
| Минусы / цена | две цифры спорят друг с другом; доверие падает | **27 планов из 210 (13 %) дольше**: медиана +2.7, максимум +14.2 мин; меняется и выбор маршрута (нужен пере-бейзлайн) | UI шумнее, голос длиннее; арифметика плана всё равно не сходится |
| Что говорит за | поведение уже принято, ничего не ломает | **единственный вариант, где числа складываются** — а именно расхождение цифр и было жалобой (§2 п.5) | минимальная правка, если менять выбор маршрутов сейчас не хочется |

Отдельно: случай «нет ни одного живого борта» (62 % запросов) во всех трёх вариантах
показывает `headway/2` — и это корректно, но цифру стоит **помечать** как расчётную, а не
фактическую (иначе она выглядит как «живое» ожидание).

## 4. Влияние на контракт лога телеметрии (§12.2)

**Ключевой факт:** роутер сейчас **не знает, откуда парк**. Сим-машины приходят с `is_live = True`
(тест `test_fleet_is_reproducible` требует ровно этого), поэтому на стенде (`GPS_SIMULATOR=1`)
UI пишет `[live]` про симулятор. Значит `source` нельзя выводить из `is_live` — источник должен
приходить из слоя парка (`live_layer` / `main.py`), иначе телеметрия будет врать ровно так же,
как `[live]` на стенде.

| Вариант | `source` ноги в ответе и логе | `had_live_data` |
|---|---|---|
| V1 | `real` \| `sim` \| `sched` — по происхождению подходящего борта; `sched`, если борт не найден | «были ли живые ТС в срезе» (не «нашёлся ли подходящий») |
| V2 | то же, но `wait_min` всегда согласован с `source` | то же |
| V3 | то же + отдельные поля `schedule_wait_min` и `live_wait_min` | то же |

Требуется добавить в ответ ноги (аддитивно, §11 брифа): `source` и, для V3,
`schedule_wait_min`/`live_wait_min`. Пометка «SIM» в UI — часть Идеи A (§3 брифа), но флаг
источника нужен уже сейчас, иначе телеметрия не отличит сим-борт от реального.

## 5. Что нужно решить (код — после решения)

1. **Вариант отображения:** V1 / V2 / V3. Рекомендую **V2**: только он делает арифметику плана
   согласованной, а цена — медиана 2.7 мин на 13 % планов. Если менять выбор маршрутов сейчас
   нежелательно (V2 его меняет → нужен пере-бейзлайн эталонов), берите **V3** как промежуточный.
2. **Поля `source` (+ `schedule_wait_min`/`live_wait_min` для V3) в `/api/plan`** — нужны для
   лога телеметрии и для пометки «SIM»; согласны ли аддитивно.
3. **Отдельно:** помечать расчётную цифру (`headway/2`) как расчётную — это 62 % запросов.

## 6. Как воспроизвести замеры

Замеры сделаны одноразовыми скриптами (в репозиторий не кладутся) с параметрами:
`seed 33`, 30 случайных пар `stop_id`, слоты 03:10 / 07:00 / 08:30 / 12:00 / 17:30 / 19:00 / 23:00,

`common.snapshot_fleet(graph, schedule, now)` → `router.set_live(fleet, snapshot_at=now)`,
`TransitRouter(..., assume_in_service=True)`; для прод-режима — `assume_in_service=False`.

Для «расхождения» использован подкласс роутера, который логирует вызовы `_wait_info` только
внутри `_build_plan` (то есть ноги выигравшего плана) и рядом берёт честный `live_wait` через
`_nearest_live_vehicle(route_key, board_node, now)`.

**Что стоит проверить повторно на реальном снимке трекера** (он вне репозитория): доля «без
живого борта» и распределение расхождения — сим-парк оптимистичнее реального.

## 7. Реализация V3 (коммит `6987b49`)

**Решение владельца: V3.** V1 отклонён (две спорящие цифры — «ложь в интерфейсе»), V2 отклонён
как отдельная поставка (меняет выбор маршрута в 13 % планов → свой пере-бейслайн), V3 принят:
план не меняется, расхождение объясняется текстом.

**Что добавлено (аддитивно):**

* в ноге плана — `schedule_wait_min` (цифра расписания), `live_wait_min` (фактическая, если живой
  борт найден) и `source` = `real` | `sim` | `sched` (`sched` — живого борта нет);
* в корне плана — `fleet_source` (`real`/`sim`) и `had_live_data` (были ли живые ТС в срезе);
* `wait_min` **не изменён** (по-прежнему `min(live, headway/2)`), поэтому поиск и планы те же;
* источник среза роутер не угадывает: `main.py` передаёт его в
  `router.set_live(..., source="sim" if isinstance(live, SimLayer) else "real")`. Без этого
  сим-машины приходят с `is_live=True`, и стенд (`GPS_SIMULATOR=1`) выдаёт симулятор за живой GPS;
* UI (`web/emulator.js`): `чекати ~5.2 хв (за розкладом)` и отдельная строка
  `↳ сідати: 5346, живий борт — через 6.9 хв [live]` — цифра, посчитанная по расписанию, помечена,
  а живой борт показан честно (см. §3, V3).

**Приёмка:**

служит маркером «источник не проставлен», в проде всегда `real` или `sim` (из `main.py`).
