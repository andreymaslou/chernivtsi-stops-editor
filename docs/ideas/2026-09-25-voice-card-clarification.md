# IDEA: голос + карточки для уточнения неоднозначного маршрута

**Создано:** 2026-09-25
**Статус:** идея / продуктовое обсуждение. Код не писали.
**Связано с:** `docs/PLAN-assistant-geo-walk.md`, `docs/BRIEF-plan-variants.md`,
`web/emulator.js`, `main.py`.

## Зачем нужна идея

Пользователь может назвать неоднозначное место:

- «універ»;
- «Кварц»;
- «майдан»;
- «банк»;
- «школа»;
- другое народное или разговорное название.

LLM не должна молча выбирать первый fuzzy-матч. Backend должен найти реальные
кандидаты в актуальном каталоге (`stops.json` + `slang_overrides.json`) и вернуть
уточнение. Варианты уточнения и маршрутные варианты — разные карточки: первые
помогают выбрать место, вторые сравнивают способы поездки.

## Главный UX-сценарий: ошибочный тап

1. Пользователь говорит: «На Кварці мені до Гравітону».
2. LLM понимает, что `Кварц` неоднозначен.
3. Система одновременно показывает карточки и озвучивает вопрос:
   - `Кварц — Головна`;
   - `Кварц — Південно-Кільцева`;
   - `Кварцова Дільниця`.
4. Пользователь нажимает не ту карточку, например `Кварц — Південно-Кільцева`.
5. Можно сразу построить предварительный/готовый маршрут, но он должен оставаться
   исправляемым.
6. Пользователь снова нажимает микрофон: «Зачекайте, я не туди клацнув».
7. Система не спрашивает заново «где вы и куда едете». Она:
   - останавливает озвучку текущего ответа;
   - очищает ошибочную линию/маршрут;
   - сохраняет уже названное направление `Гравітон`;
   - возвращает только уточнение старта;
   - показывает те же карточки или голосом предлагает варианты;
   - строит исправленный маршрут после нового выбора.

Ошибка не должна заставлять пользователя повторять всю исходную фразу.

## Голос и карточки работают синхронно

Карточка и голос — два способа завершить один и тот же диалоговый шаг:

- голосовой вопрос и карточки показываются одновременно;
- нажатие карточки сразу останавливает текущую озвучку;
- не нужно ждать окончания `speechSynthesis`;
- голосовой ответ сразу закрывает карточки;
- первый валидный ответ побеждает, повторный/устаревший ответ игнорируется;
- ошибочный выбор маршрута можно откатить без потери контекста.

Желательно делать короткую паузу перед тяжёлым построением маршрута, чтобы
пользователь успел заметить неверный тап. Но пауза не должна быть единственной
защитой: исправление голосом должно работать и после появления маршрута.

## Приоритет способов уточнения

1. Точный голосовой/текстовый ответ пользователя.
2. Нажатие карточки.
3. Выбор точки на отдельном режиме карты.
4. Явно разрешённая геолокация.
5. Свободный ответ: ближайшая улица, магазин, школа и т. п.
6. `Я не знаю` — переход к более простому объяснению, а не тупик.

Карта не должна быть обязательной: часть пользователей не знает официальных
названий остановок, не пользуется картами или не хочет включать GPS. Для них нужны
кнопки, голос и вариант `Я не знаю`.

Обычный клик по карте в редакторе остаётся намеренно заблокированным. Карта для
уточнения включается только отдельной явной кнопкой/режимом и не меняет правила
редактора.

## Предлагаемый ответ backend

При неоднозначности `/api/plan` возвращает `mode: "clarify"`, `request_id` и
структуру `clarification` с полем (`from`/`to`), исходным запросом, вопросом,
опциями и действиями. В списке опций должны быть только реальные backend-кандидаты;
LLM не имеет права придумывать `stop_id`.

Пример формы:

```json
{
  "mode": "clarify",
  "request_id": "clarify-42",
  "clarification": {
    "field": "from",
    "original_query": "Кварц",
    "prompt": "Який Кварц маєте на увазі?",
    "options": [
      {"id": "stop-113", "stop_id": 113, "name": "Кварц — Головна"},
      {"id": "stop-128", "stop_id": 128, "name": "Кварц — Південно-Кільцева"},
      {"id": "stop-159", "stop_id": 159, "name": "Кварцова Дільниця"}
    ],
    "actions": [
      {"id": "map", "label": "Показати на карті"},
      {"id": "gps", "label": "Ввімкнути геолокацію"},
      {"id": "unknown", "label": "Я не знаю"}
    ]
  }
}
```

`from_stop_id`/`to_stop_id` неоднозначного поля остаются `null`, пока пользователь
не выбрал вариант. Уже подтверждённое другое поле (`to`) должно сохраняться в
состоянии диалога.

## Границы LLM

LLM в этой идее — только транспортный диалоговый слой. Она может понять фразу,
определить намерение, сформулировать короткий вопрос и сопоставить ответ с
backend-кандидатами. Но она не выбирает первый неоднозначный fuzzy-матч, не
придумывает остановки и `stop_id`, не строит расписание и не меняет граф.

Backend проверяет `intent` и соответствие `option_id` серверному списку
кандидатов. Поэтому ограничение темы «только транспорт» должно быть не только
prompt-инструкцией, но и серверным policy/guard.


## Доступность

Пенсионеры и другие пользователи с ограничениями слуха или зрения — важная
целевая группа, но нельзя делать вывод, что все пожилые одинаково плохо слышат или
видят. Нужны одновременно несколько каналов:

- короткий голосовой вопрос;
- крупные карточки с простыми названиями;
- возможность ответить голосом;
- возможность нажать карточку;
- `Показать на карті`;
- `Включить геолокацию`;
- `Я не знаю`;
- возможность повторить вопрос;
- возможность вернуться и изменить только ошибочно выбранное место.

Оптимальный порядок — не заставлять пользователя сначала разбираться с картой или
GPS. Простые карточки и голос должны быть основным способом.

## Идея следующего этапа

Реализацию пока не начинать автоматически. Если идея будет одобрена, разбить её на
отдельные BRIF/PLAN:

1. кандидаты и серверная политика неоднозначности;
2. контракт `clarification` в API;
3. сессия/откат выбранного поля;
4. синхронизация голоса и карточек;
5. отдельный режим выбора точки на карте;
6. явная геолокация;
7. accessibility smoke-тесты и сценарии ошибки/повторного уточнения.

**Связанное решение:** голос уже реализован в `web/emulator.js` через Web Speech
API; `docs/PLAN-assistant-geo-walk.md` уже фиксирует голос, точку выхода, карту и
GPS. Этот документ фиксирует именно следующий слой — короткий уточняющий диалог.

## Откат ошибки

Фразы вроде:

- «я не туди клацнул»;
- «не тот»;
- «помилка»;
- «я переплутав»;
- «це не Кварц»;
- «ні, Головна»;

должны распознаваться как исправление конкретного поля, а не как новый полный
запрос. Система должна помнить `field`, предыдущий выбор и исходное направление.

Состояние может выглядеть так:

```json
{
  "session_id": "route-session-42",
  "state": "awaiting_from_clarification",
  "to_query": "Гравітон",
  "from_query": "Кварц",
  "previous_selection": {
    "stop_id": 128,
    "name": "Кварц — Південно-Кільцева"
  }
}
```

Для первого web-MVP можно обойтись без долгоживущей сессии: клиент заменяет
исходный текст уточнённым запросом. Для RN и голосового диалога лучше заложить
`session_id` и явные состояния диалога.
