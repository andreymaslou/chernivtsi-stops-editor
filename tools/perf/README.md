# tools/perf — замеры роутера (инструменты разработчика)

Папка для повторяемых замеров и сверок «до/после» любой правки роутера.
В рантайм сервера ничего из этого не входит; результаты пишутся в `out/`
(в git не попадает).

Все замеры детерминированы: время модельное (`2026-09-17 03:10` — ночь, парк
симулятора «вытягивает» к середине дня, поэтому цифры не зависят от того, когда
запущен замер), парк берётся из `sim_layer`.

## Запуск

```bash
python tools/perf/latency_plan.py --tag after            # слепок планов + время
python tools/perf/latency_plan.py --tag before --rev 1e16f98
python tools/perf/compare_snapshots.py before after      # побайтовая сверка + счётчики
python tools/perf/compare_snapshots.py before after --ignore-keys full_geom  # если поле добавлено сознательно
python tools/perf/ab_prod_cycle.py --old 1e16f98        # A/B в прод-режиме
python tools/perf/regimes.py                            # режимы A/B/C
python tools/perf/bench_counters.py                     # cProfile + масштабирование
python tools/perf/parity_http.py                        # локальный сервер vs VPS
python tools/perf/check_map_paths.py                    # целы ли пути ног на карте
python tools/perf/diag_stop_chain.py trolley:5:A        # цепочка остановок маршрута
python tools/perf/probe_direction.py --rev 916c286    # встречные ТС в подборе «першого потрібного ТС»
python tools/perf/check_hubs.py                          # стресс-тест хабов: выбран ли ближайший по eta ТС
python tools/perf/check_hubs.py -v                       # то же + печать каждого вызова роутера
python tools/perf/check_hubs.py --url http://127.0.0.1:8000   # + проверка живого API
```

Фразы для дымовых проверок лежат в `tools/perf/phrases/` (UTF-8), их удобно
передавать через `--text-file`, например:

```bash
python tools/perf/check_map_paths.py --text-file tools/perf/phrases/kalynka_universytet.txt \
    --url http://169.58.82.105:8000
```

`--rev` понимает `HEAD` (текущее дерево), `HEAD~1`, хеш коммита: файл
`router_layer.py` достаётся из истории git и импортируется отдельным модулем,
поэтому сравнивать ревизии можно без копирования файлов руками.

## check_hubs.py — стресс-тест сложных хабов

Инвариант: **«перший потрібний ТС» обязан быть ближайшей по eta машиной своего
маршрута, которая успевает к пассажиру**. Скрипт ловит ВСЕ фактические вызовы
`TransitRouter._nearest_live_vehicle()` во время одного `plan()` (обёртки в
памяти, `router_layer.py` не правится), независимо пересчитывает `arrive_min`
из `board_time` и `_live_snapshot_at` и падает, если:

* выбранная машина не первая среди «успевших» (впереди была другая — баг хабов);
* роутер вернул `None`, хотя подходящая машина была (или наоборот);
* `eta` / `wait_min` не совпали с пересчётом от сырой eta кандидата;
* список кандидатов не отсортирован по eta / eta < 1.0 / борт не из парка.

Проверяются и узлы, которые Дейкстра обошла, но в итоговый план не взяла.
По умолчанию — офлайн и детерминированно (парк из `sim_layer`, фразы резолвит
`Locator` по номинативным формам, LLM не нужен). `--url <base>` добавляет
проверку живого API: каждый `live_bus` из `/api/plan` обязан существовать в
`/api/live` на своём маршруте (для этого пригодился Basic Auth из `deploy/`
— передайте `-u логин:пароль`). Отчёт — `tools/perf/out/check_hubs.json`.

Текущий эталон (2026-09-17T12:00, парк 125 ТС): 5 кейсов, **9067 проверенных
вызовов, 0 нарушений**. На `--now 2026-09-17T18:30` — 10185/0.

## check_fleet_norms.py — нормы выпуска против расписания и симулятора

```bash
python tools/perf/check_fleet_norms.py
python tools/perf/check_fleet_norms.py --now 2026-09-17T12:00
```

Нормы (`data/fleet_norms.json`) — количество автобусов на маршрут в рабочие и
выходные дни из скана решения виконкому від 14.07.2026 (то же першоджерело, что
и для пільг). Скрипт проверяет ими два источника:

* «автобуси з розкладу» = час круга (`2 × one_way_minutes` з графа) / середній
  інтервал `(min+max)/2` з `routes_schedule.json` — має бути близько до норми;
  коефіцієнт поза 1.5 показує, що розклад «рідший» або «щільніший» за міську
  норму випуску;
* симулятор: у кожного напрямку мусять бути інтервал і час початку **саме з
  розкладу** (а не дефолтні `06:00/22:00/20 хв`) — це ловить клас багів, коли
  маршрут не знаходить свій рядок у файлі розпису.

Звіт: `tools/perf/out/fleet_norms_report.json`. Стан на 2026-09-26: 28 груп
маршрутів (8A і 15K успадковують норми 8 і 15), розбіжність > 1.5× у 9:
«рідший за норму» — 13 (×0.52), 15 (×0.40), 19 (×0.62), 20 (×0.51), 21 (×0.66),
5 (×0.62), 9 (×0.66); «щільніший» — 3 (×1.91), 10 (×1.86). Симулятор↔розклад —
0 розбіжностей із 76 напрямків. Маршрут 33 у документі — «Маршрутне таксі /
2,3,4,5,6,7» (без понеділка): ні розклад, ні симулятор днів тижня поки не
розрізняють.

## Ожидаемые цифры (после Шага 4, парк 119 машин)

Замеры ниже идут со ПОДКЛЮЧЁННЫМИ счётчиками (обёртки на методах) — это на
40–100 % медленнее и шумнее «чистых» прогонов, поэтому сравнивать цифры можно
только внутри одного режима. Ориентиры без инструментирования — в
`docs/REVIEW-router-latency.md` (прод-цикл 230 → 76 мс).

| Замер | Значение |
|---|---|
| `bench_counters.py`, haversine на один `plan()` | ~133 (до Шага 4 — 33 168) |
| `latency_plan.py`, p50 (ночь / день) | ~120–180 мс (`--rev 1e16f98`: ~320 мс) |
| `ab_prod_cycle.py` (set_live + plan на запрос), p50 | ~150 мс (`--old 1e16f98`: ~235 мс) |
| `regimes.py` режим A (прогрев), p50 | ~75–110 мс |
| `regimes.py` режим C (прод-цикл), p50 | ~90–150 мс |
| `parity_http.py` локально / VPS, p50 | ~100 / ~280 мс (внешние 280 мс почти целиком — сеть: `/health` 217 мс) |

## Важные грабли

1. **`set_live()` без `snapshot_at` — другой режим расчёта.** Тогда
   `arrive_min = 0`, Дейкстра обходит больше состояний (`_wait_info` ~5985 вместо
   ~4409) и `plan()` выходит ~200 мс даже с кэшем геометрии — см. `regimes.py`,
   режим B. Так мерил старый `bench3.py` (в нём ещё и счётчики не были
   подключены к классу).
2. **Кэш геометрии живёт до смены среза парка.** Прод-эндпоинт зовёт
   `set_live()` на каждый запрос, но если позиции те же (трекер отдаёт последний
   опрос), кэш сохраняется — именно это дало 230 → 76 мс
   (см. `docs/REVIEW-router-latency.md`).
3. **Разброс на рабочей машине до 2×.** Для честного сравнения запускать A/B
   подряд в одном процессе (`ab_prod_cycle.py`) и смотреть p50, а не единичные
   прогоны.
4. `latency_plan.py` пишет ПОЛНЫЙ JSON планов: ускорение нельзя принять, если
   `compare_snapshots.py` показал не `IDENTICAL: True`.
5. **`parity_http.py` без `--now` сравнивает разные часы.** Локальная машина и
   VPS берут собственное «сейчас», поэтому планы разойдутся — это разные срезы
   парка, а не расхождение кода. Для паритета передавайте модельное время явно
   (`--now 2026-09-17T03:10:00`).
6. Русские названия остановок в консоли Windows: `use_utf8_stdout()` из
   `common.py` переключает вывод на UTF-8, а полный отчёт всегда пишется в `out/`.
   Если перенаправлять вывод в файл — он тоже будет в UTF-8.
7. **Кириллическую фразу не стоит передавать аргументом из `.cmd`-файла:** cmd
   читает такой файл в OEM-кодировке (cp866) и передаёт в Python уже битый текст
   — сервер получит «╨╖ ╨Ъ╨░╨╗╨╕╨╜╨║╨╕» и ответит `mode: clarify`. Надёжные
   способы: запуск из PowerShell или `--text-file phrase.txt` (UTF-8).
   Скрипт специально сообщает «НЕ ПЛАН, а: ...» и возвращает код 2, чтобы пустой
   ответ нельзя было принять за «разрывов нет».
8. **Добавленное в план поле делает сверку красной — это ожидаемо.** Правка
   вроде `leg.full_geom` (хвосты маршруту на карте, `docs/REVIEW-map-ux.md`)
   добавляет ключ в ответ, и `compare_snapshots.py` показывает
   `IDENTICAL: False` + путь первой разницы для всех эталонных пар. Для приёма
   оптимизаций запускайте с `--ignore-keys <поле>`: список игнорируемых полей
   печатается в отчёте, так что «осознанное» отличие нельзя спрятать случайно.
